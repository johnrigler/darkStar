# Dark Star: randomized print artifacts and transaction-path TODO

This is the implementation note for making each printed copy of **Dark Star** materially unique while preserving the existing hand-edited physical pages.

## 1. Print-time random artifacts

Inject small artifacts into the existing filler / lorem-ipsum regions at **print time**, not into the authored page files permanently.

Candidate artifacts:

- tiny Pac-Man-like fruit: cherries, strawberry, simple bonus-fruit silhouettes
- small symbolic glyphs / marks, including Acoma-inspired or other explicitly chosen symbols once their use is settled
- individual QR codes
- pairs or small clusters of 2–3 QR codes
- QR codes generated by or taken from Chisel tools
- occasional human-readable Chisel / unspendable address fragments

The random layer should behave like marginal debris rather than page content. It may appear in whitespace and lorem-ipsum/filler areas, but must not obscure the authored text, comic panels, transaction text, or required QR codes.

Each invocation of a print view should generate a fresh arrangement so that two physical copies are not identical.

Prefer a client-side vanilla-JavaScript implementation. No server state should be required. A print-specific seed may optionally be displayed or encoded so a particular copy can be reproduced later, but unseeded printing should remain the default.

### Current implementation

`print-random.js` now provides the first safe slice. It decorates `pre.lorem` blocks inside the print-page iframes with 1–3 randomly selected non-QR ornaments per block. The initial pool is deliberately simple: cherries, strawberries, and a few geometric glyphs. The authored HTML pages are not modified by the randomizer.

Both `print-letter.html` and `print-booklet.html` load the module before `print.js`, and their print instructions explicitly note that reloading creates a different ornament arrangement.

This first implementation is intentionally conservative. It does not yet place QR codes, Chisel addresses, blockchain data, margin-spanning artifacts, or collision-aware free-positioned objects.

## 2. Multiple physical formats

Keep the same authored page resources and provide print transforms for:

- US Letter, 8.5 × 11, portrait, one physical book page per sheet
- US Legal, 8.5 × 14, portrait, with the same 7 × 8.5 authored area and additional vertical field available for random artifacts / marginalia
- 11 × 17 landscape booklet, duplex, imposed as the current one-fold book

The random artifact layer should use the available physical sheet, not change the dimensions of the authored 7 × 8.5 page itself.

Letter and Legal can be one-sided or two-sided as selected by the printer/user. The booklet remains the imposed duplex format.

## 3. Preface: deliberately break the narrative with the spendable transaction

`preface.html` currently has the Wake text in the left column, transformed Dogecoin-style addresses in the right column, and four QR codes below.

Preserve the existing material exactly unless a later edit explicitly changes it.

Add the missing **actual spendable transaction** as a visibly different object in the otherwise encoded/unspendable sequence. The point is to repeat the existing exception pattern: one object breaks the rule and demonstrates that this is not merely literary transformation.

Use the open space in the right-hand column to show the transaction's actual monetary value / dollar amount. It should visually interrupt the typographic system enough that a reader can recognize that this entry belongs to the ledger rather than merely to the narrative. Breaking a rule, gutter, box, alignment, background, or other visual boundary is acceptable if the reader can immediately continue through the page afterward.

Do not fabricate the transaction ID, current dollar amount, or spendability. Those values must come from the actual transaction when supplied/verified.

## 4. Bottom QR codes become a path through several persistence layers

The four QR codes at the bottom of the preface should eventually form a deliberate chain instead of four opaque placeholders.

Proposed path:

1. **Dogecoin ledger**: direct block-explorer URL for the relevant Dogecoin transaction.
2. **Polygon bounce**: a Polygon transaction whose data points onward and explicitly says, in effect, that the reader is being bounced through Polygon to the next artifact.
3. **IPFS artifact/table**: content-addressed document containing a table / map of the relevant QR codes, transaction references, Chisel encodings, and destinations.
4. **Chisel / next layer**: the actual Chisel-derived artifact or tool destination, potentially itself represented by a ledger transaction and/or IPFS resource.

The sequence should demonstrate several kinds of persistence rather than pretend they are the same thing: ledger transaction, EVM data, content-addressed IPFS object, and ordinary web/tool access.

No CID should be invented ahead of publication. Build the IPFS document first, add it to IPFS, then insert the real CID. Likewise, create/sign the Polygon transaction only after its exact payload is settled, and then replace the placeholder with the real transaction hash/explorer target.

## 5. Suggested implementation architecture

Keep authored pages dumb and printable.

Use the existing `print-random.js` as the print-only module loaded by the Letter, Legal, and booklet print shells. It should evolve to:

1. locate designated filler regions or safe page-margin regions;
2. choose a random number of artifacts per printed physical page;
3. clone SVG/HTML glyphs and QR elements from a finite artifact pool;
4. position them with collision checks against protected content;
5. vary scale and orientation within restrained limits;
6. regenerate on a fresh page load / explicit reroll;
7. freeze the current DOM automatically before `window.print()` so pagination does not mutate during printing.

Pages should opt in with simple markers such as `data-random-field` or `.print-random-field`. Do not make the individual page files dependent on a complex shared template.

A later Chisel integration can expose a plain array of QR payloads/artifacts to this module. Dark Star should consume that array without needing the rest of the Chisel UI.
