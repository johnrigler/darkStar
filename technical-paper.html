Chisel: Human-Readable Ledger Artifacts

A technical note on carrier addresses, transaction data, local interpretation, paper identity artifacts, and cross-chain verification.

John Rigler · Working draft 1.0 · September 2026 · Dark Star / Chisel / Mogwai

Abstract

Chisel is a browser-first toolkit for constructing and interpreting cryptocurrency transactions as small public artifacts. On UTXO chains, it combines deliberately chosen output addresses, output order, values, and null-data outputs. On EVM chains, it reads controlled transaction fields such as receiver addresses and calldata. A compatible reader can render these fields as language, identifiers, images, receipts, or pointers to larger content.

The central observation is limited but useful: transaction infrastructure already preserves and exposes fields that can carry meaning beyond payment. The chain supplies consensus over bytes and transaction order. Chisel supplies a human-readable interpretation. This paper specifies that boundary and states the associated limitations. It does not claim that block explorers must preserve a particular interface, that every carrier address is mathematically unspendable, or that browser-local signing is safe without verifying the code delivered to the browser.

1. Scope

This paper describes a method, not a new consensus protocol. Chisel does not ask a network to understand prose, portraits, or identity rituals. It constructs transactions that remain valid under the network's existing rules, then interprets selected fields according to an external grammar. Other software can reproduce the interpretation from the same transaction bytes.

The architecture separates three layers:

  • Ledger layer: confirmed transactions, outputs, calldata, logs, block order, and transaction identifiers.
  • Interpretation layer: Chisel's rules for decoding addresses, amounts, output order, text, image rows, and content identifiers.
  • Experience layer: Dark Star, Mogwai, games, printed artifacts, and local indexes built from decoded records.

No application can make a ledger say more than its bytes contain. Conversely, an application does not need a chain's permission to assign a reproducible meaning to fields the transaction author already controls.

2. Historical precedent

Bitcoin's genesis block contains a newspaper headline in its coinbase input. The fact is narrow: human-readable editorial language was embedded in Bitcoin data at block zero. It does not, by itself, prove that Bitcoin was intended to be a general publishing system. It does establish that a transaction record can carry both protocol function and human context.

3. Two different meanings of “unspendable”

The earlier Dark Star draft used unspendable too broadly. Chisel must distinguish two mechanisms.

Provably unspendable output: an output whose locking script cannot succeed. A conventional example is a null-data output beginning with OP_RETURN. Nodes can determine from the script itself that the output cannot be spent.

Carrier or burn-style address: a syntactically valid address deliberately constructed from chosen bytes rather than derived from a key held by the author. No usable private key is known. Spending from it is treated as computationally infeasible, but that is not the same claim as a script being logically impossible to satisfy.

This distinction matters. A familiar pay-to-public-key-hash address encodes a version and a hash-sized payload with a checksum. Constructing a valid-looking address from selected payload bytes does not prove that no private key preimage exists. It means the author did not obtain the address by generating and retaining such a key. Chisel can use the address as a durable carrier while describing the security property accurately.

A null-data output is different. Bitcoin-style OP_RETURN terminates script evaluation in failure and is explicitly used for unspendable data outputs. Relay policies, standard size limits, and fees vary by network and software version; those are operational constraints rather than a universal constant.

4. The UTXO carrier

A Chisel record can distribute meaning across ordinary transaction components:

FieldPossible useWhat consensus guarantees
Output address or script payloadReadable fragments, identifiers, labels, image rowsThe exact locking script and output position are included in the transaction
Output orderSequence and groupingThe transaction serializes outputs in a fixed order
Output valueSmall numeric code or binderThe value is part of the signed transaction
OP_RETURN dataShort text, a digest, schema marker, or content pointerThe bytes are included in a provably unspendable output
Transaction ID and block positionCitation and chronologySubject to the chain's confirmation and reorganization model

For example, a carrier string may be designed so part of the address is visually readable:

9sSADXANDXWEARYXiXGoXBACKZZZc6o8QR

The address remains a machine-validated string for the selected network. A Chisel decoder applies additional rules: prefixes can identify a schema or network; reserved characters can stand for spaces or separators; padding can fill the fixed-width carrier; and the address checksum detects many transcription errors. These interpretation rules are not enforced by the chain. They must be versioned and published so an independent decoder can reproduce them.

4.1 Indexing is useful but not guaranteed

Once a carrier output is confirmed, full nodes and indexers can derive the address or script from the transaction. Many block explorers expose address pages and search functions, making the output easy to discover without Chisel. That behavior is valuable but not a consensus obligation. An explorer may disable prefix search, filter burn-style addresses, change its interface, omit a chain, or disappear.

The durable reference is therefore the transaction identifier plus a documented decoding rule. Explorer search is a convenience layer. For stronger independence, Chisel can read raw transaction data from multiple public sources or from a local node and compare results.

5. Raster rows

The same carrier can represent data that is not language. Chisel's BASE57 image work treats an image as ordered rows. Each row is quantized to a restricted palette and encoded with an address-safe alphabet; repeated characters can represent runs of repeated colors. A checksum protects the carrier string, while the transaction and row label establish order.

#0 SNMMMBQXiiiiisrrrriiXQBBMMM12AD3f
#1 SNMMMBQXiiiippuuuuurriiiQQBMM91PT7E
#2 SNMMMBQXipppppuppupppiXXQMM9bcs4i

The rendering is not stored as a PNG in those rows. It is reconstructed by a decoder from palette and run-length rules. Independent implementations should produce the same raster from the same ordered inputs.

6. EVM extension

The method is not confined to UTXO chains. An Ethereum-family transaction contains an optional input or data field. For a contract call, those bytes normally identify a function and encode arguments. A sender can also place controlled bytes in a transaction for a decoder to interpret, subject to gas costs and the execution behavior of the destination.

Twenty-byte receiver addresses can also be chosen to resemble or encode data, but the same qualification applies as with burn-style UTXO addresses: a chosen address is not automatically a cryptographic identity, and “no known key” is not identical to “no possible key.” A contract can instead emit logs or store state under explicit rules when stronger semantics are needed.

Keeping EVM examples online is intentional. Printed Dark Star issues can point to this paper with a QR code, while the online paper can link directly to transaction explorers, contract addresses, source code, and updated decoding tools. The printed artifact remains small; the verification surface can continue to evolve.

7. Content-addressed extensions

Transactions are expensive and size-constrained compared with ordinary files. A common pattern is to place a digest or content identifier in the transaction and keep the larger object in a content-addressed system such as IPFS. A content identifier lets a reader verify that retrieved bytes match the referenced object. It does not guarantee availability by itself.

IPFS content must remain hosted or pinned by at least one reachable provider. A resilient publication should use multiple pins or providers, retain local copies, and record enough information to republish the same bytes under the same content identifier. The chain can preserve the commitment even when no current provider serves the object, but retrieval then requires someone who still possesses the bytes.

8. Verification and threat model

Chisel moves several operations into the browser, but “local” does not automatically mean “trusted.” The threat model has distinct parts:

  • Delivered-code integrity: a compromised host can serve altered JavaScript that steals keys or changes transactions before signing. Users need a trusted copy, reviewed source, reproducible hashes, offline execution, or another integrity mechanism. HTTPS protects transport, not a compromised origin.
  • RPC and proxy integrity: a proxy that never receives private keys still can omit or falsify balances, fee estimates, transactions, and chain state. Results should be compared across sources or verified against a local node when stakes justify it.
  • Signing clarity: the interface must display the exact network, inputs, outputs, values, fees, and data that will be signed. Human-readable labels are annotations, not replacements for the actual transaction.
  • Chain finality: records are subject to reorganizations and the security assumptions of the selected network. Confirmation depth should match the intended use.
  • Decoder longevity: a custom encoding survives only if its versioned specification and implementation survive. Publishing both is part of the artifact.
  • Privacy: public ledgers are not private identity stores. Correlating addresses, labels, QR codes, and physical events can create a permanent association.

9. Paper identity artifacts

Dark Star uses paper as an entry point rather than as the complete technical specification. A printed sheet can hold a portal QR code and blank positions for separately produced labels. Participants assemble the labels physically, then use the resulting artifact to enter an online tool or game.

The design goal is that no ordinary printer receives a completed private key in one printable document. That does not, by itself, make the process secure. Component generation, entropy, distribution, observation, photography, label reuse, and later key entry all affect the result. Until the complete process has been independently reviewed, the assembled artifact should be treated as educational and should not protect material financial value.

paper issue → QR or label ritual → transaction or identifier → independent retrieval → Chisel or another compatible decoder

10. What the method does and does not claim

Claim supported hereClaim not made here
Existing transaction fields can carry reproducibly decodable meaning.A blockchain understands or endorses that meaning.
A carrier address can be constructed without retaining a usable key.Every such address is mathematically proven to have no private key.
OP_RETURN can create a provably unspendable data output on compatible UTXO chains.All chains accept identical sizes, fees, or relay policies.
Explorers often make carrier records easy to inspect.An explorer is required to preserve search, prefix matching, or presentation.
Browser software can construct and sign locally.Code served by a website is automatically trustworthy.
Content addressing verifies retrieved bytes.An IPFS identifier guarantees that a provider will remain online.
The technique works across both UTXO and account-based transaction models.The security and semantics of those models are identical.

11. Reproducibility requirements

A Chisel artifact should publish enough information for an independent implementation:

  1. Network and transaction identifier.
  2. Encoding name and version.
  3. Exact character alphabet, separators, padding, and checksum rules.
  4. Rules for selecting and ordering transaction fields.
  5. Palette and run-length rules for raster records.
  6. Expected decoded bytes or digest for a test vector.
  7. Source code or compact reference implementation.
  8. Any external content identifiers and a pinning or replication plan.

Without those items, a portal screenshot demonstrates that one interface rendered something. With them, another reader can prove that the rendering follows from the recorded transaction.

12. Conclusion

Chisel's contribution is not a new place to hide arbitrary files. It is a small grammar for treating existing transaction fields as public, ordered, checksummed carriers that humans and independent software can read. The approach is intentionally modest: consensus preserves bytes; published rules turn selected bytes into artifacts; paper and narrative give people a reason to encounter them.

Dark Star can therefore remain a short printed periodical. It does not need to carry the complete history of blockchain data, the EVM extension, the security model, or every worked example. A QR code can bring the reader to this living technical layer, where claims can be corrected, examples can be linked, and additional networks can be tested without expanding the printed object.

This document describes experimental software and physical identity exercises. It is not a security audit. Do not use an unreviewed paper-key process, demonstration wallet, or experimental decoder to protect funds or credentials whose loss would matter.
